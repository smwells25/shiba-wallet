## How to read this document

Every claim in this document is meant to trace to one of four kinds of source: the project record in `AGENTS.md`, another document in `docs/`, the code (cited by file path), or an external source that one of those cites. Where a claim could not be checked, the text says "unverified" and names the way to verify it. Section 8 lists the places where the design documents and the code disagree, because in the first edition a reviewer reading `docs/ARCHITECTURE.md` alone would have come away with a stronger picture of key protection than the code delivered. Commit `3194031` rewrote ARCHITECTURE 2.4, 5.1, 5.3 and D7 to describe the code, which resolves the key-storage rows; one wording mismatch about the protection policy remains (section 8, item 13).

Likelihood and impact use a three-step scale:

| Rating | Likelihood means | Impact means |
|---|---|---|
| Low | Needs an unusual attacker position or a chain of unlikely events | Inconvenience, privacy loss of public data, or a refused operation |
| Medium | Plausible for a motivated attacker or a common user mistake | Loss of some funds, exposure of linkable private data, or a stuck account |
| High | Expected to happen to some users at mainnet scale | Loss of all funds controlled by the affected key or account |

Severity in the findings register (section 6) combines the two and adds one level, Critical, for an issue that would cause loss of funds for many users without any user mistake. No Critical finding is open today.

## Summary for leadership

The wallet is a non-custodial, React Native (Expo SDK 57) app over a pure-TypeScript engine. On testnets it has proven a wide feature set end to end, including real broadcasts on Sepolia, Bitcoin testnet3 and Solana devnet, a live WalletConnect session with Uniswap, ERC-4337 smart accounts (SimpleAccount and Kernel v3.3), an in-app EIP-7702 upgrade and revocation, and engine-level live proofs of session keys and guardian recovery.

Three conclusions matter for a mainnet decision.

1. **Plain-account features are the realistic first mainnet candidates, but not yet.** EOA sends, tokens, NFTs, swaps and WalletConnect run on code paths that are tested offline and proven on Sepolia. Before real funds, the key-storage design must be reconciled with what the code does (section 8, finding N-01: the recovery phrase is not bound to biometric authentication at the storage layer; the biometric prompt is an app-level gate), and the phone-only checks must run on a real device build (Secure Enclave or StrongBox behaviour, Face ID, release-build behaviour). Dogecoin has never broadcast a transaction.
   *Second-edition update:* N-01 is now partly mitigated. Commit `3194031` added biometric-protected phrase storage (`expo-secure-store` with `requireAuthentication`), and commit `d037fd9` added the Settings button that moves the phrase there. The policy is opt-in (CTO decision of 2026-10-02, decided by the Chairperson on 2026-10-02 (opt-in is final; the plain-feature readiness rows stay advisory because the wallet is a prototype demonstrating these features inside an account-abstraction wallet), recorded in `AGENTS.md` "Security quick wins"), so standard storage remains the default until each user chooses to move, and the protection has been proven only on the Android emulator in Expo Go (`02f6154`), not yet on a real phone. The readiness switchboard (`68b6292`) lists these plain-account features as "blocked" on mainnet with their reasons, but that status is advisory only: the features still run on mainnet unless the Chairperson decides to enforce it.
2. **Smart-account features must stay testnet-only.** Kernel v3.3 and every module the wallet installs on it (session-key permissions, guardian recovery, WebAuthn passkeys, and the 7702 delegate changes) have no published audit for the deployed versions, no confirmed bug bounty, and no stated support horizon (conditions C1–C3 from `docs/AA_FRAMEWORKS.md`). The project also found, and proved live on Sepolia, that ZeroDev's guardian validator lets a single guardian satisfy a two-of-two threshold by repeating its signature, and that guardians can sign messages as the account immediately.
   *Second-edition update:* this conclusion is now enforced in the app. The readiness switchboard (`app/src/config/readiness.ts`, commit `68b6292`) marks SimpleAccount and Kernel smart accounts, EIP-7702 upgrades, session keys, passkeys, guardians, owner rotation and paymaster sponsorship as "testnet-only" and refuses them on any network other than Sepolia before any network request is made; there is no developer override. The undo paths (revoke, remove, veto, clear settings) stay open on every network. Source: `AGENTS.md` phase 9 item 6.
3. **The remaining large risk is the user being shown something misleading.** The wallet decodes, simulates and previews before signing, refuses dApp-requested EIP-7702 authorizations, and warns on look-alike addresses. It does not verify which website a WalletConnect dApp really is, it does not decode token-permit signatures specifically, and its simulation comes from the same RPC provider as everything else it shows.
   *Second-edition update:* two of these three gaps were narrowed in commit `3194031`. The WalletConnect sheet now shows WalletConnect's Verify result (verified, unverified, mismatch or scam) and puts every approve button behind an explicit risk switch for a mismatch or scam flag (N-06), and EIP-2612 Permit, DAI-style permit and Uniswap Permit2 messages are summarised with token, spender, amount and expiry above the raw JSON (N-07). Neither has been exercised against a live dApp yet. The single-provider gap (N-10) remains: the new endpoint failover (`e2bc5bb`) improves availability only and is not a second-source check.

The top ten risks in ranked order are in section 4.13.

The code is organised as five engine packages (`packages/core`, `packages/chains-evm`, `packages/chains-utxo`, `packages/chains-solana`, `packages/prices`) and the Expo app in `app/`, which consumes the packages through `file:` dependencies.

### 1.2 Assumptions

- The user's phone runs an operating system that has not been rooted or jailbroken, and the OS keychain or keystore behaves as documented. This is an assumption, not a verified property of this app: no physical device build has run yet (`docs/DEVICE_BUILDS.md`).
- The audited `@scure` and `@noble` libraries are correct. The project validates its use of them against official test vectors and independent implementations (ethers, bitcoinjs-lib, @solana/web3.js, viem and others, per `AGENTS.md`), but does not re-audit the libraries.
- The canonical EntryPoint v0.7 contract (`0x0000000071727De22E5E9d8BAf0edAc6f37da032`, `docs/AA_STACK.md`) behaves as its source code says.
- Every network service is untrusted (ARCHITECTURE section 1). The wallet may rely on a service for availability, never for the safety of a signature.
- The user reads the confirmation screen. Several mitigations below only work if the user reads what is shown; the wallet cannot protect a user who approves an accurately described malicious request (ARCHITECTURE 5.3, residual risk).

### 1.3 Out of scope

- The security of the blockchains themselves, their consensus and their fee markets.
- The internal security of third-party contracts the user chooses to interact with through dApps (Uniswap's router, token contracts and so on), beyond what the simulation preview reveals.
- A fully compromised operating system on which the user keeps approving operations. ARCHITECTURE 5.1 states plainly that no software wallet can defend this case; this document only notes where the design narrows it.
- Physical attacks on the secure element or TEE hardware.
- Store distribution security (code-signing infrastructure at Apple, Google and Expo), except where the project's own configuration affects it.
- Features that do not exist yet: in-app browser, push notifications, fiat on-ramp, staking, hardware wallets, MPC, cloud backup. Where `docs/ARCHITECTURE.md` describes such features, they are design intent only.
- A legal review. The licensing question about (L)GPL and AGPL modules is recorded as an open item for counsel (finding F-39), not analysed here.

## 2. Assets to protect, ranked

| Rank | Asset | Where it lives | Why it matters |
|---|---|---|---|
| 1 | **Recovery phrase (BIP-39 mnemonic)** | `expo-secure-store` under `shiba-wallet.mnemonic.v1` with `WHEN_UNLOCKED_THIS_DEVICE_ONLY` (`app/src/wallet/storage.ts`), or, once the user opts in, under `shiba-wallet.mnemonic.v2` in the biometric-protected class (keychain service `shiba-wallet.protected`; commit `3194031`, section 3.2); transiently in JavaScript memory when loaded | It derives every key on every chain, including every smart-account owner and every EIP-7702-upgraded EOA (ADR D1). Its loss to an attacker is total loss for all seed-derived accounts. |
| 2 | **Derived private keys** | Never stored; re-derived per signing operation in `WalletContext.signWith` (`app/src/wallet/WalletContext.tsx`) and held in a signing closure until the operation finishes | Each key controls one account on one chain family. EVM accounts share a non-hardened parent, so one leaked EVM key plus the EVM parent extended public key would expose every EVM account (ADR D8, "shared EVM subtree"); the app never exports an extended public key. |
| 3 | **Funds in smart accounts and upgraded EOAs**, including counterfactual (undeployed) addresses | On-chain; addresses computed locally (ADR D4) | A counterfactual address can receive funds before its contract exists. Correct local address computation is what makes those funds recoverable. After an owner rotation the address can no longer be computed from any seed (finding F-37). |
| 4 | **Session keys** | `expo-secure-store` via `sessionKeyVault` (`app/src/wallet/storage.ts`), one entry per chain, account and permission id (`shiba-wallet.session-key.v1.<id>` standard, or `shiba-wallet.session-key.v2.<id>` protected when the phrase is protected; section 3.2); public grant data in AsyncStorage | A session key can spend within its on-chain grant until expiry, without any further user interaction. For ERC-7715 grants the dApp, not the wallet, holds the session key (`app/src/wallet/sessions.ts`). |
| 5 | **Passkey credentials** | Private key inside the platform authenticator; only public data in AsyncStorage `shiba-wallet.passkeys.v1` (`app/src/wallet/passkeys.ts`) | A passkey installed on a Kernel account can spend from it and, because Kernel lets it make self-calls, could replace the root owner if the app's client-side guard were bypassed (finding F-19). |
| 6 | **Guardian keys** (held by other people) | Outside this wallet, except when this wallet acts as a guardian for someone else | Enough guardian weight can replace the account owner and can sign messages as the account immediately (finding F-20). |
| 7 | **Recovery metadata** | AsyncStorage `shiba-wallet.recovery-records.v1` and `.recovery-progress.v1`; exported as QR, text or a `.json` file (`app/src/wallet/recovery.ts`, `app/src/components/RecordFileActions.tsx`) | Secret-free, but after an owner rotation it is the only reliable way to find the account again. It also reveals guardian addresses and the labels the user gave them. |
| 8 | **WalletConnect sessions and smart-account bindings** | Reown WalletKit's own persistence; bindings in AsyncStorage `shiba-wallet.wc-smart-bindings.v1` | A live session lets a dApp queue signing requests at any time. Bindings decide which account a request may act for. |
| 9 | **Third-party service credentials the user pastes** (bundler, paymaster, history and NFT indexer URLs with embedded keys, 0x key, Blockbook key, CoinGecko Demo key) | AsyncStorage (`aa.ts`, `indexer.ts`, `nfts.ts`, `swap.ts`, `blockbook.ts`, `prices.ts`) | Not key material, but their theft costs the user money or quota with the vendor and can deanonymise them to that vendor. |
| 10 | **User privacy**: the link between the user's addresses, their IP address, their contacts and their balances | Spread across AsyncStorage and every network request | Every service the wallet contacts sees the device IP and some of the user's addresses (section 4.8). |

### 3.2 Device secure storage

The mnemonic is written with `SecureStore.setItemAsync(MNEMONIC_KEY, mnemonic, { keychainAccessible: WHEN_UNLOCKED_THIS_DEVICE_ONLY })` (`app/src/wallet/storage.ts`). The module comment describes this as "the iOS Keychain on iOS and the Android Keystore-encrypted SharedPreferences on Android". Session private keys use the same storage class. No other key material is stored.

What is known:

- The accessibility class means the item is meant to be readable only while the device is unlocked and is not migrated to a new device by OS backups (comment in `storage.ts`, consistent with ARCHITECTURE 2.4).
- The app never passes a `requireAuthentication` option to `expo-secure-store` (a search of `app/src` finds none). The stored phrase is therefore **not** bound to a biometric or passcode event at the storage layer; any code running in the app process while the device is unlocked can read it. The biometric prompt is a separate, app-level check (section 3.3). This differs from the design in ARCHITECTURE 2.4 and D7 (see section 8).

What is not known:

- Whether the Android key that wraps the stored values is StrongBox-backed or TEE-backed, and whether iOS stores the item with any Secure Enclave involvement, has **not been verified on real hardware**. `AGENTS.md` lists "real Secure Enclave/StrongBox" as phone-only and unverified, and `docs/DEVICE_BUILDS.md` lists it among the checks for the first device build.
- The emulator runs proved persistence across restarts and the absence of screenshots on the seed screens; they say nothing about hardware backing.

The two bullet lists above describe the first edition's evidence (`860e552`). Commit `3194031` changed the storage layer, and the following subsections describe it at `02f6154` (code at `d037fd9`). The statement that "the app never passes a `requireAuthentication` option" is no longer true: it now does so for the protected class below, but only after the user opts in.

#### 3.2.2 What the protected class does, per platform

These facts come from the installed `expo-secure-store` 57.0.4 sources, as recorded in `AGENTS.md` ("Security quick wins") and in the `storage.ts` header:

- **Android:** the value is encrypted with an AES-256-GCM Keystore key created with `setUserAuthenticationRequired(true)` and no validity window. Every read and write shows a BiometricPrompt with a CryptoObject. Only strong (class 3) biometrics are accepted and there is no PIN fallback (the negative button is Cancel). A phone without an enrolled strong biometric cannot use the class.
- **iOS:** the Keychain item carries `SecAccessControl` with `biometryCurrentSet`. Reads and updates prompt; creation does not. The app needs `NSFaceIDUsageDescription`; the `expo-secure-store` config plugin writes a default one for development and store builds, but Expo Go on iOS lacks it, so the phrase stays standard there.

#### 3.2.3 Policy: opt-in

`PHRASE_PROTECTION_POLICY` in `storage.ts` is `'opt-in'` at `d037fd9`. The phrase moves into the protected class only when the user presses "Protect with biometrics" in Settings (commit `d037fd9`), after a confirm dialog that explains the invalidation rule below. The alternatives `'automatic'` (move whenever the device can) and `'off'` are one constant away and are covered by `check-storage.mjs`. This is a CTO decision of 2026-10-02 that is **decided by the Chairperson on 2026-10-02: opt-in is final**; the builder had first implemented `'automatic'` (`AGENTS.md` "Security quick wins", "POLICY DECISION").

The move is a recorded state machine that cannot lose the phrase: find the standard copy, check eligibility (strong biometrics), write the protected copy, read it back and compare (a mismatch, cancel or empty read deletes the protected copy and stops), record "protected" in the meta entry, then delete the standard copy. If that last delete fails, the next protected read deletes the standard copy only if the two are identical. An unreadable protected copy with a standard copy present falls back to the standard copy. A new wallet never silently replaces a readable different one. Source: `AGENTS.md` "Security quick wins".

#### 3.2.4 The invalidation rule

A protected entry is **permanently invalidated** by the operating system when the enrolled biometrics change: on Android when a fingerprint or face is added or all are removed, or when the screen lock is turned off; on iOS when a finger is added or removed or Face ID is re-enrolled. From then on this phone can never read the protected phrase, and the user must restore the wallet from the written backup. On Android an invalidated key makes reads return nothing; the app reports this in plain words instead of treating the wallet as missing. This trade-off is the reason the policy is opt-in. Source: `AGENTS.md` "Security quick wins" ("INVALIDATION RULE"), `storage.ts` header.

#### 3.2.5 What is still not known about the protected class

- Hardware enforcement: the emulator's Keystore is software-only, so emulator runs can prove the flow, not the hardware property. The flow itself is now proven on the Android emulator in Expo Go (`AGENTS.md` Settings protection entry, recorded in `02f6154`): two system prompts for the move, one prompt for a reveal, no prompt at launch.
- First edition of this list: whether `requireAuthentication` works inside Expo Go on Android. **Now verified** on the Android emulator by the same run (`02f6154`).
- The unreadable (invalidated) state has not been exercised on the emulator; the dark-mode layout of the Settings section has not been eyeballed.
- Everything on iOS: invalidated reads, Face ID disabled for the app, and Expo Go's refusal text.
- Whether the 30-second hold (section 3.3) always covers the time from approval to signing; if not, the user sees one extra prompt.

Sources: the "UNVERIFIED" list in `AGENTS.md` "Security quick wins" and the Settings protection entry recorded in `02f6154`.

### 3.3 The JavaScript runtime

All app code, the engine, React Native and every npm dependency (including the WalletConnect WalletKit tree, which raised the Android bundle from 884 to 1,709 modules when it was added, per `AGENTS.md` phase 3 candidate 5) run in one Hermes JavaScript realm. There is no process or realm isolation between the signing code and the dependencies.

Signing flow (`WalletContext.signWith`):

1. A screen first calls `requireLocalAuth` (`app/src/wallet/biometric.ts`). This shows the OS biometric prompt with the OS passcode as fallback (`disableDeviceFallback: false`). If the device has no biometric hardware or no enrolment, the function returns `{ ok: true, gated: false }` and the action proceeds without a prompt, by documented design.
2. `signWith` loads the mnemonic from secure storage, computes the 64-byte seed, derives the active account's key through `deriveSignerFor`, refuses unless that key controls exactly the address the operation was quoted for, runs the signing callback, and zeroes the seed in a `finally` block.

Second-edition change (commit `3194031`, `AGENTS.md` "Security quick wins"): when the phrase is in the protected class, `requireLocalAuth` first opens the protected phrase, so the operating system's biometric prompt is the user's verification, and the opened phrase is held for the signing call that follows: one use, at most 30 seconds (`PHRASE_TICKET_TTL_MS` in `storage.ts`), and dropped when the app goes to the background (not on iOS "inactive", which the Face ID prompt itself triggers). The user therefore sees one prompt per operation, and the approval is biometric-only: after a biometric lockout signing waits, although the auto-lock screen still unlocks with the passcode. When the phrase is in the standard class, step 1 is unchanged. No `signWith` call site changed in that commit. Flows that still show two prompts: a session-key test operation, a session-key install on Android, and the Android migration itself (write, then read back).

Memory facts from the code: the seed buffer is zeroed after every use. The protected-phrase hold described above keeps the phrase string reachable for up to 30 seconds after the prompt. The mnemonic is a JavaScript string (returned by `expo-secure-store` and passed to `mnemonicToSeed`), which cannot be zeroed. The derived private key is captured by a signing closure in `packages/core/src/chains/*.ts` and is not explicitly zeroed; it becomes unreachable when the closure is dropped and is left to the garbage collector. ARCHITECTURE 5.5 already accepts the garbage-collector copy risk; the string and closure cases go beyond what that section describes (section 8).

The gate is enforced by convention at each call site, not inside `signWith`. Every current `signWith` call site in `app/src/screens/*` and `app/src/wallet/WalletConnectContext.tsx` was checked for this document and is preceded by a `requireLocalAuth` call in the same flow; the passkey path is the documented exception, where the platform passkey prompt is the user-verification step (`AGENTS.md` phase 8 item 3, app half). A future call site that forgets the gate would sign without a prompt, so a reviewer should treat "every `signWith` is gated" as a property to re-check on each change. That check was made for the first edition at `860e552` and was not repeated call by call for the second edition; `AGENTS.md` records that commit `3194031` changed no call sites. With a protected phrase, a forgotten gate would no longer sign silently, because opening the phrase itself raises the system prompt; with a standard phrase it still would.

### 4.13 Top ten risks, ranked

1. **Key storage is weaker than the design** (N-01). The phrase is not bound to biometric authentication at the storage layer; the biometric prompt is an app-level gate, and phones without enrolled biometrics have no wallet-level gate at all. *Second edition:* partly mitigated by opt-in biometric-protected storage (`3194031`, `d037fd9`); standard storage stays the default until the user opts in, and nothing has been verified on real hardware.
2. **Unaudited smart-account stack** (C1–C3; F-14, F-18, F-21, F-25). No published audit covers Kernel v3.3, its 7702 changes, the permission policies, the recovery modules or WebAuthn v0.0.3.
3. **Guardian validator weaknesses** (F-20). Repeated signers satisfy thresholds (proven live), and guardians can sign as the account immediately.
4. **Phishing through typed-data signatures** (T-13, N-07). Permit and Permit2 messages are shown as raw JSON with a generic warning. *Second edition:* Permit, DAI-style permit and Permit2 now get a summary card (`3194031`); other schemas still fall back to the generic listing.
5. **Unverified dApp identity** (T-11, N-06). The dApp name and URL on every sheet are self-reported. *Second edition:* WalletConnect's Verify result is shown and a mismatch or scam flag needs an explicit risk switch (`3194031`); unverified over the live relay.
6. **Single-provider truth** (T-21, N-10). Simulation, pre-flight, balances and risk facts all come from one RPC, with no cross-check. *Second edition:* unchanged; the new failover (`e2bc5bb`) adds availability, not a second source.
7. **Passkey self-call caveat** (F-19). The guard that stops a passkey from replacing the owner exists only in this app.
8. **Supply chain in one JavaScript realm** (T-40). Every dependency can reach the signing path, and version ranges are not exact. *Second edition:* CI and a pre-commit secret scan now run (`1e37343`); the realm and version-range exposure is unchanged.
9. **Unverified phone-only behaviour** (sections 3.2 and 3.6). Hardware backing, Face ID, release-build behaviour and Android backup of AsyncStorage have not been checked on a real device.
10. **Recovery and lifecycle gaps** (T-51 to T-55). After an owner rotation the account cannot be derived from the seed, grants survive a wipe, there is no account discovery and no BIP-39 passphrase.

### 7.2 The reproduction entry points (second edition)

Since commit `1e37343` the whole offline verification is one command at the repository root, documented in `docs/CONTRIBUTING.md`. A reviewer should start here rather than running suites one by one:

```sh
npm ci
(cd app && npm ci)
npm test              # offline: engine build + vitest, every offline app suite,
                      # expo lint --max-warnings 0, app tsc, Android export
npm run test:live     # the same plus live suites and live sections
                      # (read-only; keyed endpoints only when .dev-wallet/env exists)
npm run secret-scan   # the secret scan over the committed tree (HEAD)
npm run hooks:install # enable the pre-commit secret scan for this clone
```

- `npm test` runs `scripts/ci/run.mjs` in offline mode. That runner imports nothing from the code under test. It preloads `scripts/ci/offline-guard.mjs` into every child process, which refuses every network connection except loopback and makes `.dev-wallet/` look absent, and a step that attempts any network connection fails even if the suite tolerated the refusal. It also fails on a non-zero exit, a failed count, a missing summary line or a timeout (the whole process group is killed). Every script in `app/scripts/` must be classified in `scripts/ci/suites.mjs` (`offline`, `flag-live`, `env-live`, `live` or `helper`); the runner refuses to start otherwise. Partial runs: `npm run test:engine`, `test:app`, `lint`, `typecheck`, `bundle`; options after `--` such as `--only`, `--skip-bundle`, `--verbose` and `--logs-dir`.
- `npm run test:live` is for developer machines only. It adds the live sections of the `flag-live` suites, the key-dependent sections of the `env-live` suites (`check-doge`, `check-indexer`) and the always-live scripts (`check-balances`, `check-history`).
- The pre-commit hook (`scripts/githooks/pre-commit` → `secret-scan.mjs`) scans staged files; CI scans the whole checked-out tree before `npm test`. Rules, the allow list and the never-print-a-value behaviour are in `docs/CONTRIBUTING.md` and T-56.
- CI (`.github/workflows/ci.yml`): one job on Node 24, `npm ci --ignore-scripts` for both trees, the tree secret scan, then `npm test`; read-only permissions, no secrets, SHA-pinned actions, logs uploaded only on failure. Recorded results: runs for `12b311c` and `1e37343` succeeded (runs 37081746661 and 37082671263), the run for `3194031` succeeded including the bundle export, and the run for `d037fd9` succeeded (`AGENTS.md` phase 9 item 4, "Security quick wins" and the Settings protection entry). #### Dogecoin mainnet demonstration

`scripts/testnet/doge-mainnet-demo.mjs` performs the single real Dogecoin broadcast that W6 asks for. It derives the dev wallet's Dogecoin address (`m/44'/3'/0'/0/0`, which must equal `DEQ788Pe98Z97Le6feBa2P49JL7ETGSMNf` or the script refuses to run) and builds a 1 DOGE self-send through the app's own `prepareUtxoSend` with the Blockbook backend: UTXOs and the fee estimate come from NOWNodes' Dogecoin mainnet Blockbook (`GET /api/v2/estimatefee/6`, converted exactly to sat/vB with the 1000 sat/vB floor), and the engine's coin selection and legacy P2PKH signing produce the transaction. Before anything is signed for broadcast it checks that the backend reports coin `Dogecoin` on chain `main` and the Dogecoin genesis hash, that the fee is at most 2 DOGE and at most 5% of the amount, that any change output is at least 0.01 DOGE (Dogecoin Core 1.14.9's soft dust limit; the engine's generic 546-unit floor is lower), and that every input and output belongs to the dev address. The signed transaction is then decoded independently with bitcoinjs-lib: the txid, the output scripts and amounts, the fee, the 0x1e address version byte, and each signature against bitcoinjs's own legacy sighash.

The default run is a dry run that prints all of this and stops; with no balance it prints the funding instruction (about 5 DOGE to the address above) and exits. `--fake-utxos` runs the same path fully offline against one fake 10 DOGE UTXO and can never broadcast. Broadcasting requires both `DOGE_MAINNET_BROADCAST=1` and typing the exact txid at the prompt; the script then sends the transaction through the app's `sendUtxo` (`POST /api/v2/sendtx/`), polls `GET /api/v2/tx/{txid}` for up to 20 minutes (`DOGE_DEMO_POLL_MINUTES`), reports "seen in mempool" or "confirmed N", and prints how to check the txid on the Blockbook host or any Dogecoin Core node. The API key is sent only in the `api-key` header and is never printed.

To check a claimed on-chain result independently, take the transaction hash recorded in `AGENTS.md` and read its receipt from any Sepolia RPC (`eth_getTransactionReceipt`); for 7702 runs also read `eth_getCode` of the EOA, which must be `0xef0100` followed by the Kernel implementation address while delegated and `0x` after revocation.

### 7.6 What a reviewer cannot reproduce without inputs

## 8. Places where the documents and the code disagree

This section exists so that no reader is misled by an older design text. Each item states what the document says, what the code does, and what to do.

Second-edition status: commit `3194031` rewrote ARCHITECTURE 2.4, 5.1, 5.3 (items 2 and 4) and D7 to match the code (`AGENTS.md` "Security quick wins"), which resolves items 1, 2 and 6 below. Items 3, 4, 5, 7, 8, 9, 10 and 11 are unchanged; item 12 is settled in the record; items 13 and 14 are new.

1. **Hardware-gated key storage.** ARCHITECTURE 2.4, 5.1 and ADR D7 describe envelope encryption with a Secure Enclave or Keystore key that requires biometric presence, so that "the seed blob is undecryptable without a hardware-verified biometric event". The code stores the phrase directly in `expo-secure-store` with `WHEN_UNLOCKED_THIS_DEVICE_ONLY` and no `requireAuthentication`, and gates actions with an app-level `requireLocalAuth` prompt (`storage.ts`, `biometric.ts`). Either implement the design or amend ARCHITECTURE to match (W1, N-01). **Resolved (second edition, commit `3194031`):** the custom envelope was not built; instead the code gained an opt-in protected class (`requireAuthentication`), and ARCHITECTURE 2.4, 5.1 and D7 now describe the two storage classes, the invalidation rule and the app-level gate as they are. One wording mismatch remains about the policy (item 13).
2. **Wallet-level passcode.** ARCHITECTURE 2.4 says the app "additionally supports a wallet-level passcode". The recorded decision in `lock.ts` is that there is no app PIN. ARCHITECTURE should be amended. **Resolved (second edition, commit `3194031`):** ARCHITECTURE 2.4 now says "There is no wallet-level passcode" and cites the decision in `lock.ts`.
3. **BIP-39 passphrase.** ARCHITECTURE 2.1 and 5.2 describe an optional passphrase for generation and import. The core supports it; the app does not offer it (N-02).
4. **Memory hygiene.** ARCHITECTURE 5.5 says secrets never live in JavaScript strings and every secret buffer is zeroed. The mnemonic is a string and derived keys are not zeroed; the seed is (N-03). Second edition: still open for 5.5, which was not rewritten. ## Appendix A. Glossary

- **Bundler:** a service that collects ERC-4337 UserOperations and submits them to the EntryPoint contract.
- **Counterfactual address:** the address a smart account will have once deployed, computable in advance with CREATE2.
- **EIP-7702 authorization (tuple):** a signature by an EOA that sets its code to point at a delegate contract.
- **ERC-1271 / ERC-6492:** how contracts validate signatures, and how that works before the contract is deployed.
- **ERC-5792:** the wallet call API dApps use to request atomic batches.
- **ERC-7715:** a draft standard for dApps to request scoped execution permissions (session keys).
- **Guardian:** another key holder who can approve an owner change on a Kernel account.
- **Kernel v3.3:** ZeroDev's ERC-7579 modular smart account, the wallet's production candidate.
- **Paymaster:** a contract and service that pays gas for a UserOperation.
- **Session key:** a separate key allowed to act for a smart account within on-chain limits.
